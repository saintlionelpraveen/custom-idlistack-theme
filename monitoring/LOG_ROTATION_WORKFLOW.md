# Ghost Log Rotation & Centralized Logging – Minikube Environment

## 1. Overview
This document explains the end-to-end workflow for implementing log rotation for Ghost logs in our Minikube cluster environment. The objective is to manage Ghost logs efficiently by:
- Limiting the size of each log file to 20 MB
- Maintaining only the latest 3 active logs
- Moving older logs to Google Drive as an archive
- Automating the archiving process using a systemd watcher service
- Preparing logs so they are actively collected by Loki/Promtail for centralized logging

This setup ensures logs do not grow indefinitely while still preserving historical logs for debugging and monitoring, and offering real-time views in Grafana.

## 2. System Architecture (Minikube Setup)

```text
       Ghost Application
               ↓
 Ghost Log Files (Winston Logger)
 (~/ghost/log_rotating/active)
               ↓
 Systemd Watcher Script (ghost-archive-watcher.sh)
               ↓
 Google Drive (archive)  <-- AND -->  Promtail → Loki → Grafana (real-time)
```

## 3. Ghost Log Location
Ghost stores logs in the following directory:
`~/ghost/log_rotating/active`

Example files:
`log-2026-03-24.log.1`
`log-2026-03-24.log.2`
These files contain JSON-formatted runtime logs generated by the custom Winston logger.

## 4. Log Rotation Requirements
The system was configured with the following rules:

| Rule | Description |
|------|-------------|
| Maximum Log Size | 20 MB |
| Maximum Active Logs | 3 (Fallback 10 in Winston) |
| Old Logs | Uploaded to Google Drive |
| Archive Location | `gdrive:ghost-logs/archive/` |

## 7. Log Rotation Script
A Javascript custom logger (`custom-logger.js`) handles rotation at 20MB, and a shell script (`ghost-archive-watcher.sh`) manages cloud archiving.

Preview of the crucial `ghost-archive-watcher.sh` content:
```bash
#!/usr/bin/env bash

ACTIVE_DIR="/home/praveen/ghost/log_rotating/active"
RCLONE_DEST="gdrive:ghost-logs/archive"
KEEP_FILES=3

# Identifies excess files beyond KEEP_FILES
for (( i=0; i<excess_count; i++ )); do
    file="${log_files[$i]}"
    gz_file="/tmp/${filename}.gz"
    
    # Compress
    gzip -c "${file}" > "${gz_file}"
    
    # Upload & Only delete on success
    if rclone copy "${gz_file}" "${RCLONE_DEST}/" ; then
        rm -f "${file}"
        rm -f "${gz_file}"
    fi
done
```

## 8. Script Permissions
Make the watcher script executable:
```bash
chmod +x ~/ghost/monitoring/ghost-archive-watcher.sh
```

## 9. How Log Rotation Works
The script performs the following operations:
1. Scans all `log-*` files in the active directory
2. Checks the count of logs
3. If the active files exceed the limit of 3 files:
   - Identifies the oldest logs
   - Compresses them to a temporary `.gz` file
   - Uploads them to Google Drive via `rclone`
   - Safely deletes the local active file **only** after a successful upload
   - Ensures exactly 3 active logs remain locally

Example archived file in Google Drive:
`log-2026-03-24.log.1.gz`

## 13. Automating Log Rotation Using Systemd
To automate log rotation, a `systemd` service was created instead of a standard `cron` job, providing continuous polling and better stability.

Install and start the service:
```bash
sudo cp ghost-archive-watcher.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now ghost-archive-watcher
```
Meaning: Run continuously in the background executing `ghost-archive-watcher.sh`.

## 14. Verifying Systemd Job
Check scheduled service status:
```bash
sudo systemctl status ghost-archive-watcher
```
Expected output:
```text
Active: active (running)
```

## 15. Final Workflow

```text
       Ghost Application
               ↓
        Generates logs
               ↓
  ~/ghost/log_rotating/active
               ↓
 Systemd watcher polls active directory
               ↓
         If logs > 3 files
               ↓
 Oldest log compressed and uploaded
               ↓
 Local log deleted safely
               ↓
 Only 3 active logs maintained
```

## 16. Benefits of This Setup
- Prevents logs from growing indefinitely locally
- Maintains system stability without blocking Node.js memory
- Preserves historical logs permanently in the cloud
- Enables flawless real-time integration with centralized logging systems as local logs sit cleanly in `active/`

## 17. Current Stage (Cluster Logging)
In this current stage, logs are actively collected directly from the active files using:
a. **Promtail** (log collector mounted securely into Minikube)
b. **Loki** (log aggregation server storing chunks for 7 days)
c. **Grafana** (visualization interface)

Logs are pushed from Promtail to Loki, where they can be queried in milliseconds perfectly avoiding duplicate scraping.
